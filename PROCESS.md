# Process

## Milestone 1: map view

Built the Next.js app in `web/` per ARCHITECTURE.md and web/AGENTS.md. Scope: map selector, match list, canvas minimap with journeys, event markers, zoom/pan, hover tooltip, legend. No playback or date filters yet.

### Data layer
`lib/types.ts` mirrors the JSON shapes exactly. `lib/loadData.ts` fetches index.json then a map's JSON on selection. `lib/journeys.ts` does one pass over the parallel `rows` arrays (already sorted by player then time, per ARCHITECTURE.md) to build a `Map<matchIndex, Journey[]>` — grouping by player boundary (`p[i]` changing) and then bucketing by the player's `match` field. This runs once per map load, so switching matches after that is just a Map lookup, no re-scan.

### Rendering
`MapCanvas` draws the minimap and journeys on a single canvas, transform-based (translate/scale) so zoom and pan are just a `{scale, tx, ty}` update plus a redraw, not a re-render. Devicewise DPR is handled by sizing the backing store to `clientWidth*dpr` and scaling the context. Bot paths draw first (dashed gray, path only) then human paths on top (solid blue), then markers on top of that, human journeys only, per ARCHITECTURE.md's note that bot-side combat events duplicate the human side. Marker size and line width are divided by the current scale so they stay a constant size on screen regardless of zoom level.

Hover uses screen-space hit testing (recomputed on pointer move from the current transform) rather than tracking DOM elements per marker, since a busy match can have a few hundred markers and re-rendering that many DOM nodes on every pan/zoom would be slower than a canvas redraw.

### Decisions
- **Map switch remounts the canvas (`key={mapMeta.id}`), match switch doesn't.** Switching maps resets zoom/pan to fit (makes sense, it's a different image and coordinate space). Switching matches within the same map keeps the user's current zoom/pan, so they can compare matches at the same spot on the map without re-finding it.
- **Default match = the one with the most non-movement events**, so the initial view is never an empty map with a single 10-second journey on it. The sidebar auto-scrolls to and highlights that match on load.
- Next.js 16 / eslint-config-next ships React Compiler lint rules (`react-hooks/refs`, `react-hooks/set-state-in-effect`) that flag ref reads during render and unconditional `setState` in effect bodies. Reworked the canvas component to keep pan/zoom in a ref (read only inside imperative draw calls and event handlers, never during render) and used the "compare prop to previous-render state, conditionally setState during render" pattern for clearing the hover tooltip when the match changes, instead of resetting it in a `useEffect`.

### Testing
No browser tool was available in this session by default, so I installed Playwright + Chromium locally (scratchpad only, not a project dependency) and drove the running dev server: loaded the app, switched maps, switched matches, zoomed (wheel), panned (drag), and hovered markers to confirm the tooltip. Checked the browser console for errors on each of these. Also ran `npm run lint` and `npm run build` clean.

## Data observations (for INSIGHTS.md)

**The per-match `events` field in the data double-counts kills/deaths for matches with several bots, because it sums rows from both sides of a fight.** Example: AmbroseValley, match `de5aa1ae-6246-4cfb-9941-adf5996ef678` (Feb 12, index 463 in the map's match array). `matches[463].events` reports `BotKilled: 11`, which looks like the human died 11 times in one match. Checking the raw rows: the human player in that match (`1429`, one of the numeric-ID players that moves like a human per ARCHITECTURE.md) has **zero** `BotKilled` rows of its own — all 11 come from the 14 background bots' own logs of their own deaths. Same pattern on `BotKill`: 4 of the 12 are the human's, 8 are bots killing other bots. So `matches[i].events` is a raw sum across every player's file in the match, not deduplicated the way ARCHITECTURE.md says the heatmap data is. I didn't touch the pipeline (out of scope), but I stopped using `match.events` for the sidebar's kill/death/loot summary and instead compute it client-side from the human-only journeys — the same data source the map markers use — so the sidebar text and the markers on screen always agree. If a later milestone (or someone reading `AmbroseValley.json` directly) uses `matches[i].events` for anything human-centric, it needs the same correction.

**The numeric-ID players that move like humans aren't one-off.** `1429` (AmbroseValley) shows up as the lone human in 14 separate matches spanning Feb 10 to Feb 14, with `humans: 1` in all but one of them. Real human players in this dataset are mostly single-match (per ARCHITECTURE.md, "most matches only have one human file"), so a numeric ID appearing as *the* human across 14 matches over 5 days stands out — it behaves less like a one-off classification edge case and more like a persistent test/QA account that happens to move like a player. Worth a note in INSIGHTS.md if player counts or "unique humans" get cited anywhere, since this one ID would otherwise be silently folded into "human" totals 14 times over. The other two flagged IDs (`1402` on Lockdown, `1379` on GrandRift) each show up in only 1–2 matches, so they read more like the ordinary bot-shaped-like-a-human edge case.

**No teleporting/jump artifacts found in position data.** Checked all three maps for consecutive same-player position samples with implausibly large uv-space jumps in a short time window (would show up as a path snapping across the map) — found none. Movement paths are clean; whatever noise exists in this dataset is in the event/kill counting, not the positions.

**Loot and kill markers cluster tightly around a few structures**, consistent with INSIGHTS.md's point 2 — e.g. AmbroseValley match `d3a3297e-2cdf-4a49-8450-09119b91a779` (index 74, the highest-activity match on that map: 1 human vs 13 bots, 12 kills, 10 deaths, 68 loot) has almost all of its loot and kill markers sitting on top of two building clusters, with long empty stretches of path between them. Re-checking this same match with the corrected human-only summary (see below), it's actually 6 bot kills and 68 loot with zero deaths — the human extracted.

## Milestone 1 review fixes

`lib/markers.ts` is the one function (`buildJourneyMarkers`) both the canvas draw loop and the hover hit-test now call, so the marker list, z-order (loot → start → extraction → combat/death), and tooltip content can't drift apart between what's drawn and what's hoverable — that was an asymmetry risk once markers stopped being a one-to-one map of raw event rows.

Verified in-browser (Playwright again, browser tools weren't connected this session either): opened a bot-heavy match (13 bots), confirmed dashed gray bot paths render distinctly from the solid blue human path at multiple zoom levels, confirmed hover tooltips on both new marker types ("Journey start" / "Extracted safely" with correct player id and timestamp), confirmed the sort dropdown reorders the list correctly for all three modes, and confirmed the legend now lives in the sidebar and no longer overlaps the map. No console errors. `npm run lint` and `npm run build` both clean.

### Where journeys end, by map

Counted human journeys with no death event in their own row log (i.e., the run ends in extraction rather than a kill/storm marker) against ones that do have a death event, per map:

- **AmbroseValley**: 568 human journeys, 252 extracted (44%) vs 316 died (56%). Extraction points aren't dominated by one exit — the busiest 10x10-grid cell only holds 46 of 252 extraction points (18%), spread across at least 5 noticeably-used cells. Reads as multiple viable extraction routes rather than a single chokepoint.
- **Lockdown**: 171 human journeys, 74 extracted (43%) vs 97 died (57%). More concentrated than AmbroseValley — the top cell holds 14 of 74 (19%) extraction points, and given this is also the map where storm deaths are disproportionately common (INSIGHTS.md point 3), it's worth checking in playback (next milestone) whether the extraction cluster and the storm-death cluster are competing for the same route.
- **GrandRift**: only 59 human journeys total, so this is a thin sample, but 29 extracted vs 30 died with the top grid cell holding 9 of 29 (31%) extraction points — more concentrated than either other map, though I wouldn't treat this as solid given the sample size (same caveat INSIGHTS.md already gives GrandRift's storm-death numbers).

Death rate (56–57%) is close to even across AmbroseValley and Lockdown despite them being very different map sizes, which was mildly surprising going in — I expected the smaller, closer-quarters Lockdown to run hotter than that relative to Ambrose Valley.

## Overlapping markers fix

Multiple event rows can land on the exact same map point (same second, same u/v) — this isn't rare; besides the two flagged kill/death cases, repeated Loot rows at an identical spot (a player picking up several items in one place across a couple of seconds) show up constantly in the data. Previously these just drew on top of each other in array order, so a death marker could end up hidden under a loot circle drawn after it.

Fixed by giving every marker type a fixed priority rank (`lib/markers.ts`, `MARKER_PRIORITY`): start, loot, bot kill, player kill, extracted, then killed-by-bot, killed-by-player, storm-death last, so death events always draw on top no matter what else shares the spot. The canvas draw pass sorts by this rank once per match (memoized), and the hover hit-test reuses the same sorted list and rank, so drawing order and tooltip order can never disagree with each other. Hovering now collects every marker within the existing 9px hit radius instead of just the closest one, sorted highest-priority first, and the tooltip renders each as its own line (deduping the player-id line when consecutive items belong to the same player, since in every case I found they do). A thin white ring is drawn around the top-priority marker of any stack, computed each draw call from the live zoom level (so it stays accurate as you zoom, rather than being baked in at one scale) — cheap since a single match's marker count is small enough that the O(n²) proximity check is a non-issue even during drag/zoom.

Re-verified both flagged cases in-browser (screenshots, not just data-level checks):
- GrandRift, match `711c9a67-dd8c-4070-90e4-c606b89c007d` (Feb 10, 7m 12s, index 5): the human's own log has a `Kill` row and a `Killed` row at the identical timestamp (t=431s) and identical position. The death (X) marker now renders on top with the white stack ring, and the tooltip reads "Killed by another player · 7:11" then "Killed another player · 7:11" — matches the requested example exactly (this is the one PvP encounter in this dataset where you can see both sides of the trade from a single human's file, since the counterpart's own file wasn't loaded as human-tracked data here).
- GrandRift, match `faa11b06-6248-4ba0-a269-ec013c35f88f` (Feb 10, 8m 39s, index 6): `Loot` and `BotKilled` both at t=519s, same position, right at the very end of the run. The death (downward triangle) marker now renders on top with the ring, tooltip reads "Killed by a bot · 8:39" then "Loot picked up · 8:39".

**On the GrandRift 7m 12s trade kill specifically**: this is one of only 3 player-vs-player fights in the whole dataset (per the death-cause breakdown in INSIGHTS.md point 1 — 403 deaths to bots, 39 to storm, 3 to other players). A `Kill` and a `Killed` row on the *same human's own file* at the identical second and identical position reads as a trade: this player killed their opponent and died in the same instant, standing on the same spot. With PvP already this rare, the one clean example of it in the data being a mutual kill rather than a clean win is worth a mention if INSIGHTS.md's PvP section gets expanded later.

## Milestone 2: timeline playback

### What was built
A timeline bar under the map (scrubber, "3m 05s / 13m 15s" readout, Play/Pause/Restart, 1x/2x/4x/8x with 4x default, event ticks coloured by type that jump to their time on click). Paths now draw progressively up to the playhead with a dot at each player's current position. Space toggles play/pause, left/right step 5s. Switching match or map builds a new clock at 0, paused. Speed is kept across matches since it is a viewing preference, not match state.

### Decisions
- **The clock is a small class outside React** (`lib/playbackClock.ts`) that owns the requestAnimationFrame loop and notifies subscribers only when time changes. The canvas subscribes directly and redraws imperatively, so no React render happens per frame. Only the timeline readout uses `useSyncExternalStore`, so the 566-row match list never re-renders during playback. Pause cancels the frame loop, so nothing runs while paused.
- **Two stacked canvases.** The minimap image is on a base canvas redrawn only on pan, zoom or resize; paths, dots and markers are on an overlay redrawn per frame. Marker list, priority sort and tracks are memoized per match. The stack-ring proximity check is cached by (marker set, zoom, visible count), since visible markers only grow with time.
- **Interpolation** (`lib/playback.ts`): linear between consecutive samples, binary search for the segment. Gaps over 30s are not interpolated: the dot holds at the last sample and jumps when the next arrives, and the drawn path breaks across the gap instead of drawing a line through missing data. Checked against real journeys (35s and 40s gaps in AmbroseValley) and a midpoint interpolation.
- **Dot disappears at the first death event, or at the last sample for extraction**, and the path stops growing there. 124/16/35 journeys (Ambrose/GrandRift/Lockdown) have rows after their first death (the "177 rows after death" from ARCHITECTURE.md); those rows are ignored for the path and dot but their markers still show.
- Markers appear when the playhead reaches their time and stay; hover and the tooltip only consider markers already visible.
- Bots get a small grey dot and a dashed path, humans a larger blue dot with a white ring, so the two differ by size and shape as well as colour. Both are in the legend.
- Scrubbing pauses while dragging and resumes on release if it was playing. Timeline buttons blur after clicking so Space does not double-trigger a focused button.
- At t=0 the map is empty apart from start markers. That follows the spec (reset to 0 and pause) but a designer who wants to see a whole route now has to drag to the end. A faint "ghost" of full paths or a show-all toggle would fit the upcoming filters milestone.

### Bug found while restructuring
The old canvas effect re-fit the view every time `draw` changed identity, which included match switches and hover changes. So "match switch keeps your zoom" from milestone 1 was not actually guaranteed by the code. Fitting now runs only when the image loads. Verified: zoom survives a match switch and mouse movement over the map.

### Verification
Playwright against the production build: play/pause/space, arrow steps (+5, -5), click-to-seek, tick click, end-of-match shows Restart, match switch resets to 0m 00s and pauses, no console errors. Performance on AmbroseValley `b971c686-07f6-4378-ad00-71b0b610414e` (Feb 10, 12m 09s, 1 human + 14 bots) at 8x for 6s: 355 frames, avg 16.7ms, p95 16.8ms, max 16.8ms, zero long tasks (headless, so a floor rather than a guarantee for slower machines).

## What playback shows that static paths did not

Numbers below are from the cleaned data (human journeys over 7 minutes for the movement stats), plus watching playback on AmbroseValley `d3a3297e-2cdf-4a49-8450-09119b91a779`, AmbroseValley `b971c686-...` and Lockdown `18c1b2c6-4f87-4200-9816-68fa448de33b` (13m 44s, ends in a storm death). I did not play through a GrandRift match this round, so GrandRift numbers here are data-only and from a small sample.

**Bots move in groups, and mostly from a small set of spawn points.** In the 14-bot AmbroseValley matches, 46% of bot samples have another bot within 0.02 map units, against about 11% if the same positions were placed at random. Static paths just looked like a tangle; in playback you can see pairs and small groups travelling together. Only 32 distinct start cells (2% grid) cover 268 AmbroseValley bots, and 5 cells hold 39% of them (Lockdown 28 cells for 124 bots, GrandRift 24 for 52). Bots that share a spawn are still only about 0.065 map units apart after 60 seconds, so routes out of a spawn are similar rather than identical. The bots feel semi-scripted: shared spawns, group travel, near-constant motion.

**Bots never stop, humans do.** Stationary share of samples is about 1% for bots and 8-11% for humans; bot speed at p10 is still 1.1 units/s on AmbroseValley versus 0.29 for humans.

**Bots die early and vanish.** 75% of bot journeys (200 of 268 on AmbroseValley) end before 90% of the match, median bot death about 3.4 minutes in on AmbroseValley (206s), 4.4 on Lockdown (265s) and 2.6 on GrandRift (154s). In a bot-heavy match the map is crowded for the first few minutes and near-empty later, which fits INSIGHTS.md point 1 (deaths happen early).

**No single direction late in the match.** If the storm pushed everyone one way, late movement would line up. Direction of travel over the last 40% of long human journeys has a concentration of 0.15 (AmbroseValley), 0.23 (Lockdown), 0.19 (GrandRift) on a 0 to 1 scale, so mostly random. What does show is a radial pattern: median distance from the map centre falls from 0.38 to 0.16 over the first 70% of a journey on AmbroseValley (0.30 to 0.19 Lockdown) and then rises again to 0.24 in the last 30%. Players converge on the middle to loot and then head back out, which is consistent with extraction points being scattered rather than central.

**Storm deaths are mid-map, not at the edge, and late.** AmbroseValley storm deaths (17) have median time 730s and sit near the centre (mean position 0.43, 0.49, median centre distance 0.19), in cells (4,6) and (4,3). Lockdown (17) median 761s, mean 0.55, 0.54. The storm catches people who stayed in the middle rather than people who ran into an edge. In Lockdown `18c1b2c6-...` the route loops around the eastern side of the map for most of the run (judged by eye at 30/60/90% of the match, not measured) and the storm death lands at the east edge at 13m 44s, so this one looks like a long stay rather than a blocked route. INSIGHTS.md point 3 already flags Lockdown storm deaths; playback suggests looking at dwell time rather than route blockage.

**Lots of dwelling and backtracking.** Median path length is 3.8x the straight-line distance on AmbroseValley and Lockdown and 6.8x on GrandRift (small sample), the longest stay inside a 0.03-unit circle is a median 17% of a journey, and about 15% of samples revisit an area first visited at least 60s earlier. Static paths look like purposeful routes; playback shows looting clusters where the dot sits for a minute or more, then a move.

**Sampling caveats.** Mean absolute heading change per 5s step is about 1 radian for both humans and bots, so 5s sampling is too coarse to show real steering. The dot's smooth motion is interpolated, not observed. Gaps over 30s are 187 (AmbroseValley), 21 (GrandRift), 81 (Lockdown), mostly human journeys (159, 14, 51), so humans are more likely to have missing stretches than bots.
